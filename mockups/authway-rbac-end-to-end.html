Authway RBAC — End-to-End Integration

Bức tranh tổng quan: Zimbra LDAP → ZITADEL (identity) → authway-rbac (roles/permissions) → SDK trong app → per-app resource ACL. Plan 260812-1150-authway-central-rbac.

CORE PRINCIPLE

Zitadel quyết định bạn là ai (identity, SSO, MFA). authway-rbac quyết định bạn được làm gì (roles, permissions). App quyết định được làm trên resource nào (per-app ACL).

LDAP INTEGRATION (đã configure)

Zimbra LDAP = identity source thật. Zitadel federate LDAP — user login qua Zitadel Console, credential verify về LDAP; Zitadel sync metadata (email, department) vào chính nó.

authway-rbac KHÔNG nói chuyện trực tiếp với LDAP — chỉ sync từ Zitadel. Lý do: single source of truth, Zitadel đã translate LDAP → OIDC sub, trust boundary đơn giản, deactivation flow tự động qua session expiry.

Reference: plan 260806-1504-sso-multi-app-zitadel-ldap-rollout.

4. Permission naming + OneLog dogfood seed

NAMING SPEC

<service>.<resource>.<action>

Kebab-case, singular resource, verb action.

  • service: onelog, cloud, s3, monitoring
  • resource: topic, alert, dashboard, bucket
  • action: read, list, create, update, delete, silence, ack

Wildcard: cho phép svc.resource.*. CẤM *.* (F4 — silent priv esc).

ONELOG SEED (Validation V4)

Dogfood targets: Grafana + VMAlert

Permissions: onelog.grafana.read onelog.grafana.admin onelog.alert.read onelog.alert.silence onelog.alert.ack onelog.alert.create onelog.dashboard.read onelog.dashboard.create Roles (explicit, no *.*): onelog.viewer ├── onelog.grafana.read ├── onelog.alert.read └── onelog.dashboard.read onelog.oncall (inherits viewer +) ├── onelog.alert.silence └── onelog.alert.ack onelog.admin (explicit ~10) └── all onelog.* enumerated

5. Admin workflows

GRANT ROLE

CLI (Phase 4a — 1 ngày)

$ authway-rbac assign \ --user=trihd@inet.vn \ --role=onelog.oncall → Resolve email → Zitadel sub → Upsert users (lazy sync if missing) → INSERT user_roles → Bump users.permissions_version → Emit audit_log (hash-chained) → Ship stdout → OneLog rsyslog → SDK poll notices ≤ 30s
EMERGENCY REVOKE

Immediate deny (bypass cache)

$ authway-rbac deny-now \ --user=trihd@inet.vn \ --until=2026-12-31T00:00Z \ --reason="incident-42" → SET users.deny_until = ... → SDK check on every request → 403 → Audit: severity=critical → Alert phòng KT
BREAK-GLASS (Zitadel down)
  1. Zitadel outage → cannot login Admin UI or verify JWT
  2. Retrieve break-glass token from sealed secret (phòng KT)
  3. curl -H "X-Break-Glass-Token: <token>" https://rbac.auth/admin/...
  4. authway-rbac bypasses JWT verify, executes with actor=break-glass:<hostname>
  5. Emit metric authway_break_glass_used_total → alert
  6. Post-incident: authway-rbac break-glass rotate → new token

6. Zitadel ↔ authway user sync

PHASE 0 SPIKE B GATES THIS

Nếu Zitadel v4 Actions V2 hỗ trợ webhook lifecycle events → Option A (real-time). Nếu không → Option B (lazy + reconcile).

OPTION A (preferred)
Zitadel event (user.added/changed/ deactivated/removed) │ │ HTTP POST + HMAC(timestamp||body) ▼ authway-rbac POST /internal/sync/user ├── verify HMAC + timestamp skew ≤ 5min ├── dedup (event_id, ts) in-mem LRU ├── check event.change_date > local ├── upsert users + bump version └── audit + invalidate cache + Reconcile every 5min: list Zitadel users → diff → upsert Alert: drift > 1% OR > 10 OR webhook_events rate = 0 15min
OPTION B (fallback)
/authz/me arrives với unknown sub │ ▼ authway-rbac ├── verify JWT (Zitadel issuer) ├── extract sub ├── users.zitadel_user_id │ ├── FOUND → normal flow │ └── MISSING → fetch Zitadel API │ upsert users, proceed └── Deactivate detected via: - Zitadel session expires - Periodic reconcile flags stale

7. Security layers

IDENTITY

Zitadel

  • LDAP federation (Zimbra)
  • MFA enforce policy
  • OIDC PKCE
  • JWT signed (JWKS rotate)
  • Event-sourced audit
TRANSPORT

IAP boundary

  • oauth2-proxy per app
  • Caddy TLS + IP allowlist
  • Trust IAP header từ allowlisted upstream
  • Reject direct requests
AUTHZ

authway-rbac

  • JWT verify (iss + aud + sig)
  • client_id allowlist
  • Rate limit per user
  • Bootstrap CLI one-shot fuse
  • Break-glass audit + alert
  • DB role split (audit INSERT-only)
  • Hash-chain audit rows

10. Zitadel alone — làm được gì (không cần RBAC)

Zitadel là IdP hoàn chỉnh, KHÔNG chỉ auth qua LDAP. Nó có sẵn nhiều primitive authorization dùng được ngay.

Capabilities sẵn có

CapabilityChi tiết
Identity + FederationLDAP bind (đã setup), password, MFA (TOTP/Passkey/SMS), SSO
OIDC/OAuth2 issuerAccess token, ID token, refresh token, JWKS, PKCE
OrganizationsMulti-org, org policy (password, MFA, login)
Projects (~= Apps)Mỗi app = 1 Project. Register OIDC client, define scopes
Zitadel RolesPer-Project: define roles (key + display_name + group). VD project onelog có roles viewer, oncall, admin
Authorization GrantsAssign User↔Role per Project. Embedded vào ID token dưới claim urn:zitadel:iam:org:project:roles:*
Delegated adminOrg owner, Project owner, User manager
Audit identity eventsLogin, MFA, user CRUD, role grant/revoke (event-sourced)
Session managementSession TTL, force logout, session listing
Actions V2Enrich token, call webhook (limited — Phase 0 verify)
Admin Console UICRUD user/role/project/grant — technical UI
Password reset, self-serviceCó sẵn

Ví dụ: OneLog chỉ dùng Zitadel

Setup Zitadel: Project = "onelog" Roles (declared in project): onelog-viewer, onelog-oncall, onelog-admin User trihd@inet.vn assigned role "onelog-oncall" trong project onelog Login flow: User login → Zitadel issue ID token với claim: "urn:zitadel:iam:org:project:roles": { "onelog-oncall": {"proj-id": "onelog"} } App (OneLog): Parse JWT → thấy role → if role == "onelog-oncall" then allow silence

Kết luận: Zitadel CÓ authorize được, nhưng ở role level thô, không có permission granular <svc>.<rsc>.<action>. Đủ dùng cho scale nhỏ 1-2 app; đau khi scale ra 5+ app hoặc cần fine-grained control.

CHỌN ZITADEL ALONE NẾU
  • OneLog + max 1-2 app khác trong 12 tháng
  • Role thô đủ (viewer/oncall/admin)
  • Chấp nhận Admin qua Zitadel Console
  • Cache invalidation qua token TTL 15min OK
  • Không cần audit permission catalog changes
  • Không cần emergency deny nhanh

Effort: 1-2 ngày.

CHỌN CENTRAL RBAC NẾU
  • Có ≥ 3 app committed adopt (F1 gate)
  • Cần permission <svc>.<rsc>.<action> để scale
  • Ops phòng KT không muốn học Zitadel Console
  • Cần deny_until emergency
  • Cần break-glass ngoài Zitadel
  • Cần centralized audit + hash chain

Effort: 2-3 tuần.

HYBRID (Option C — chưa chốt)

Zitadel + thin Go library + YAML in Git: Zitadel giữ role assignment, library authway/pkg/rbac map role name → permission list từ YAML, middleware RequirePermission(). Effort ~1 tuần. Không có deny_until, không có Web UI, permission phân tán per app.

Middle ground: có convention permission nhưng không có service riêng. Có thể upgrade lên Option B sau khi có 3+ app.
