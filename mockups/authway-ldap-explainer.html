What is LDAP

LDAP = "directory protocol" — cách legacy để lưu & query user/group của tổ chức.

LDAP (Lightweight Directory Access Protocol) là chuẩn 1993, chạy trên TCP :389 (LDAP) hoặc :636 (LDAPS). Nó lưu user/group dạng cây (DN — Distinguished Name, ví dụ uid=alice,ou=people,dc=inet,dc=vn) và cho phép app "bind" bằng username+password để verify. Active Directory của Microsoft, OpenLDAP, FreeIPA, 389DS, lldap đều là LDAP server. LDAP KHÔNG phải OIDC — nó không có access token, không có scope, không có consent screen; chỉ có bind/search/modify. App muốn dùng LDAP phải tự implement client (Java JNDI, Python ldap3, PHP ldap_*...) — không portable như OIDC.

📇 Directory tree (DN) 🔐 Simple bind (u/p) 🌳 Hierarchical (dc/ou/cn) 🏢 Corp legacy (AD) ⚠️ No token/scope/consent

0  Từ viết tắt · glossary

Đọc trước nếu chưa quen từ vựng identity
Viết tắtNghĩa · giải thích ngắn
LDAPLightweight Directory Access Protocol — chuẩn 1993, TCP :389/:636, để query/verify user trong directory tree.
LDAPSLDAP over TLS (port 636). Encrypted end-to-end. Bắt buộc ở production.
StartTLSKỹ thuật upgrade plain LDAP :389 lên TLS trong cùng connection. Thay thế LDAPS.
ADActive Directory — LDAP server + Kerberos của Microsoft, chạy trên Windows Domain Controller. LDAP-compatible.
DCDomain Controller (server chạy AD) · hoặc Domain Component (phần tử trong DN, ví dụ dc=inet,dc=vn). Tùy ngữ cảnh.
DNDistinguished Name — đường dẫn unique tới 1 entry trong LDAP tree. Ví dụ uid=alice,ou=people,dc=inet,dc=vn.
BaseDNĐiểm bắt đầu search trong tree. Ví dụ dc=inet,dc=vn = search toàn domain.
Bind DNDN dùng để bind (login) vào LDAP server. Thường là service account.
OUOrganizational Unit — thư mục con trong tree, ví dụ ou=people, ou=groups.
CNCommon Name — tên hiển thị của entry (thường là full name).
UIDUser ID — username unique trong LDAP (OpenLDAP). AD dùng sAMAccountName.
Viết tắtNghĩa · giải thích ngắn
IdPIdentity Provider — hệ thống xác thực user (Zitadel, Google, Okta, AD, ...). Trả về ai đó "là ai".
SPService Provider — app cần biết user. Nhận identity từ IdP.
SSOSingle Sign-On — login 1 lần, vào nhiều app không phải nhập lại pw.
MFAMulti-Factor Authentication — thêm yếu tố ngoài pw (TOTP, passkey, SMS).
TOTPTime-based One-Time Password — mã 6 số đổi mỗi 30s (Google Authenticator, Authy).
OIDCOpenID Connect — chuẩn auth trên OAuth 2.0, phát id_token (JWT). Modern thay thế LDAP/SAML.
OAuth2Chuẩn authorization (delegate quyền truy cập). OIDC = OAuth2 + identity layer.
JWTJSON Web Token — token có chữ ký, chứa claim (email, roles...). Format của id_token.
SAMLChuẩn SSO cũ (XML-based). Enterprise vẫn dùng nhiều.
JITJust-In-Time provisioning — auto tạo user trong Zitadel ở lần login đầu (thay vì import trước).
IAPIdentity-Aware Proxy — pattern proxy sidecar (oauth2-proxy) chặn request chưa auth, giống Google Cloud IAP / Cloudflare Access.
CACertificate Authority — bên phát cert TLS. Self-signed = tự ký, phải cấu hình trust riêng.
DN, RDNRelative DN = phần đầu tiên của DN (uid=alice). DN = RDN + parent path.
Tool cụ thể
OpenLDAP — LDAP server open-source phổ biến (Linux).
FreeIPA — bộ suite IdM của Red Hat (LDAP + Kerberos + DNS).
389DS — LDAP server của Red Hat, kế thừa Netscape Directory.
Bridge tool
GlAuth — LDAP server nhỏ dạng Go, config bằng TOML/YAML.
lldap — LDAP server nhẹ (Rust), có web UI.
ForumSys — LDAP test public (ldap.forumsys.com).
Stack Authway
Zitadel — IdP self-host (Go, AGPL). OIDC/SAML/LDAP-IdP.
oauth2-proxy — IAP sidecar, OIDC client.
Traefik — reverse proxy + TLS termination.
Thuật ngữ khác
Bind — hành động "login" vào LDAP.
Filter — biểu thức search LDAP, ví dụ (uid=alice).
objectClass — schema xác định attr nào hợp lệ cho entry.
memberOf — attr chứa DN group user thuộc.

Auth flow (simple bind)
sequenceDiagram autonumber participant App participant LDAP as LDAP server App->>LDAP: BIND uid=svc,dc=inet,dc=vn (svc pw) LDAP-->>App: OK App->>LDAP: SEARCH base=ou=people, filter=(uid=alice) LDAP-->>App: dn=uid=alice,ou=people,dc=inet,dc=vn App->>LDAP: BIND that dn + alice's pw LDAP-->>App: OK / INVALID

Pattern: service bind → search DN → bind lại bằng pw user. Không token, session tự app quản.

2  Zitadel × LDAP · ma trận hỗ trợ

Hai chiều khác nhau, đừng nhầm
CHIỀU A · ✅ GA

LDAP làm Identity Provider của Zitadel

User gõ URL app → oauth2-proxy → Zitadel login page → user chọn "Login with LDAP" → Zitadel bind vào AD/OpenLDAP verify → JIT tạo user trong Zitadel → phát OIDC token cho app.

  • 🎯 Use case: team đã có AD/LDAP, không muốn tạo lại password store
  • 🔒 Self-hosted Zitadel only (Cloud Zitadel bị chặn)
  • 🧬 JIT provisioning hoặc account linking
  • 🔁 One-way: LDAP → Zitadel copy attribute lúc login. Không write-back.
CHIỀU B · ❌ KHÔNG hỗ trợ

Zitadel làm LDAP Server cho legacy app

Muốn legacy app (GitLab CE cũ, Jenkins plugin, backup tool, Nextcloud, MediaWiki, SonarQube phiên bản LDAP-only...) bind vào Zitadel qua LDAP protocol → không được.

  • 🚫 Request từ 2020 (discussion #1929) — team Zitadel không có capacity
  • 🛠️ Workaround: chạy LDAP bridge (GlAuth, lldap) trước Zitadel, hoặc migrate app sang OIDC
  • 💡 90% app "hiện đại" đều có mode OIDC → thử enable trước khi nghĩ tới bridge

4  Chiều B · Nếu bắt buộc cần Zitadel-as-LDAP

Workaround bằng bridge
Option 1 · GlAuth / lldap bridge

Chạy 1 container LDAP nhỏ (GlAuth, lldap) làm "shadow directory", đồng bộ user từ Zitadel qua Management API. Legacy app bind vào bridge; bridge không tự verify password mà proxy về Zitadel (khó — vì Zitadel không expose password verify endpoint).

⚠️ Thực tế phải duplicate user + password store — mất ý nghĩa "SSO". Chỉ dùng nếu số app kẹt < 3.

Option 2 · Migrate app sang OIDC

Ưu tiên. Hầu hết app phổ biến (GitLab, Jenkins, Nextcloud, Grafana, Vault, Argo CD, Harbor, Gitea) đều có OIDC/OAuth2 built-in hoặc plugin. Migrate 1 lần, hết đau đầu.

✅ Khớp với triết lý Authway: "1 app = 1 OIDC client".

BƯỚC 1Recon Zimbra LDAP config

SSH vào Zimbra, chạy dưới user zimbra để lấy config LDAP thực tế:

ssh zimbra-mail
su - zimbra -c 'zmlocalconfig \
  ldap_url ldap_master_url ldap_port \
  ldap_starttls_supported ldap_common_loglevel \
  zimbra_ldap_userdn'

# Lấy password service account (SECRET):
su - zimbra -c 'zmlocalconfig -s zimbra_ldap_password'

# Xem port đang listen:
netstat -tlnp | grep -E ':(389|636)'
BƯỚC 2Lấy BaseDN thật & sample user

Dùng chính LDAP để tự khám phá schema:

# BaseDN (namingContexts):
ldapsearch -x -H ldap://localhost:389 -s base -b "" namingContexts

# List 5 user đầu:
ldapsearch -x -H ldap://localhost:389 \
  -D "uid=zimbra,cn=admins,cn=zimbra" \
  -w "$(su - zimbra -c 'zmlocalconfig -s zimbra_ldap_password' | cut -d= -f2 | xargs)" \
  -b "" -s sub \
  "(objectClass=zimbraAccount)" \
  uid mail givenName sn cn zimbraAccountStatus | head -60

Đảm bảo service account bind được:

# Bind thành công = có quyền search:

  -D "uid=zimbra,cn=admins,cn=zimbra" \
  -w "$ZIMBRA_LDAP_PASS" \

BƯỚC 4Mở LDAP port ra Authway VPS

Mặc định Zimbra chỉ listen 127.0.0.1. Có 2 option:

  • Option A (đơn giản): SSH tunnel từ Authway VPS ssh -L 3389:localhost:389 zimbra-mail → Zitadel bind vào ldap://localhost:3389. Dev/test OK.
  • Option B (prod): Bind slapd trên 0.0.0.0, restrict firewall (ufw allow from <authway_ip> to any port 636), bật LDAPS proper.
# Firewall Zimbra (nếu Option B):
ufw allow from $AUTHWAY_VPS_IP to any port 636 proto tcp
ufw allow from $AUTHWAY_VPS_IP to any port 389 proto tcp
BƯỚC 5Export CA cert cho LDAPS

Zimbra tự sinh cert self-signed → Zitadel sẽ reject. Copy CA:

# Trên Zimbra:
cat /opt/zimbra/conf/ca/ca.pem

# Trên Authway host (nơi chạy Zitadel container):
scp zimbra-mail:/opt/zimbra/conf/ca/ca.pem \
    /etc/docker/certs/zimbra-ca.crt

# docker-compose.yml của Zitadel:
volumes:
  - /etc/docker/certs/zimbra-ca.crt:/etc/ssl/certs/zimbra-ca.crt:ro
# → restart zitadel container để reload CA store

BƯỚC 7Add LDAP IdP trong Zitadel Console

Vào https://authway.inet.vn/ui/console → chọn Instance (hoặc Org) → Identity Providers → + New → Active Directory / LDAP. Điền theo section 5 phía trên. Chú ý:

  • Bật Auto Register để JIT tạo user.
  • Bật Auto Update để mỗi lần login refresh givenName/sn/cn từ Zimbra.
  • Có thể enable Account Linking để user đã tồn tại (nếu từng tạo native) sẽ được gộp.
  • Save → click nút Activate ở góc phải (mặc định inactive).

Mở private/incognito → truy cập 1 app phía sau Authway:

  2. Thấy nút "Login with Zimbra LDAP" → click

BƯỚC 10Debug khi fail
  • Zitadel logs: docker logs -f zitadel hoặc journalctl -u zitadel -f → tìm dòng có ldap.
  • Zimbra slapd logs: tail -f /opt/zimbra/log/ldap.log → thấy bind request từ IP Authway.
  • Cert issue: báo x509: certificate signed by unknown authority → CA chưa mount đúng, xem lại bước 5.
  • Bind fail: báo invalid credentials → sai password, chạy lại bước 1 lấy password.
  • User not found: filter sai, thử đổi (|(uid=%v)(mail=%v)) hoặc kiểm tra BaseDN.
  • JIT không tạo: attribute mapping thiếu email → phải bật auto register + đủ 4 field email/username/first/last.

7  Gotchas & limitations

Đọc trước khi commit
Vấn đềChi tiếtCách né
Cloud blocked Zitadel Cloud không cho LDAP IdP (network access issue) Authway self-host → OK
Cert self-signed Một số version Zitadel bug khi verify LDAPS cert self-signed Dùng CA proper (mkcert / step-ca) hoặc downgrade cẩn thận
Plain LDAP :389 Không encrypted, password bay trong subnet Bắt buộc LDAPS :636 hoặc StartTLS trong production
No realtime sync Disable user ở AD → Zitadel không biết ngay, chỉ chặn login lần sau Script cron kiểm tra + disable qua Management API, hoặc dùng short session
One-way copy Đổi tên/email trong Zitadel không sync ngược về LDAP AD/LDAP là source of truth; sửa ở đó
Group mapping Zitadel không auto map memberOf sang project role Dùng Actions (script custom) hoặc set role manual
MFA double Nếu AD đã có MFA + Zitadel cũng enforce → user MFA 2 lần Chọn 1 layer, thường Zitadel (passkey UX tốt hơn)
